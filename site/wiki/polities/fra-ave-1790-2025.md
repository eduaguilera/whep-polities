# Aveyron (département)

## Summary

Aveyron is a département in south-central France (Occitanie region since 2016), seat at Rodez, corresponding closely to the historic province of Rouergue. It is one of the roughly 83 original départements created by the Revolutionary reform of 4 March 1790, and its boundary has been stable since -- it is not one of the four documented departure cases for France's default start rule (it is not Belfort, not part of the Alsace-Lorraine trio, not Corse, and not an overseas département). type is subnational because Aveyron has never been sovereign: it is an administrative subdivision of France throughout its existence, sitting below the national FRA chain in the containment hierarchy the same way Spain's provinces (ESP-AS, ESP-CA, ...) sit below ESP. The routing decision proposed start_year 1790, matching the Revolutionary creation date, but the polity table's earliest FRA national container is FRA-1800-1871 -- there is no FRA row covering 1790-1800 to contain an 1790-1800 slice of Aveyron, and the containment gate rejects an edge that falls outside either party's span. start_year is therefore clamped to 1800, the earliest year a container exists for, rather than left at the historically accurate 1790; see decisions below.

**Why this entry exists.** The routing decision (unit_id FRA-FRJ22, admin_name FRJ22) captures a mitchell/NUTS-style series for Aveyron with data spanning 1862-2023, entirely inside the proposed 1790-2025 span. Before this entry, the only FRA candidates in the polity table were the national-level rows (FRA-1800-1871, FRA-1800-1919, FRA-1871-1919, FRA-1919-2025) -- a département-level series was previously unmatched or would have been misrouted to the national row, which is roughly 550,000 km2 against Aveyron's own ~8,700 km2, a mismatch of nearly two orders of magnitude that a national row cannot represent honestly. Aveyron's status as a distinct, stable administrative and statistical reporting unit since 1790 is confirmed by its continuous listing as a département in INSEE's own administrative geography and by its NUTS3 code (FRJ22) in the EU's regional statistics nomenclature, which is the classification the source data (admin_name FRJ22) is keyed to.

## Decisions

### d-start-year-clamped-to-1800

**start_year set to 1800, not the proposed 1790**

The routing decision's span_basis argues correctly that Aveyron dates to the 4 March 1790 Revolutionary reform, and proposes start_year 1790. But the polity table's earliest FRA national row is FRA-1800-1871 (data/final/polities_database.csv row 284) -- there is no FRA container covering 1790-1800. The containment gate this repository runs rejects any container edge that falls outside either party's own span, and 'container edges must tile the whole span' is a hard requirement here: a 1790-2025 span containered only from 1800 would leave 1790-1800 uncontained, exactly the failure mode the instructions warn against (using USA-1959-2025 to contain 1850-2026 as the counter-example). Rather than invent a container for 1790-1800 that doesn't exist in the table, or leave a decade uncontained, start_year is clamped to 1800 -- the earliest year for which a container edge exists. This means the entry's frontmatter start_year (1800) does not match the routing decision's proposed start_year (1790); the code FRA-12-1800-2025 reflects the clamped value, since 'the years in the code must equal the years in the frontmatter'. If a pre-1800 FRA container is later added to the table, this entry's start_year and code should be revisited back toward 1790.

### d-polygon-not-assigned-despite-registered-source

**polygon_source recorded as the registered slug, feature left null**

The routing decision's polygon_route is registered_source_unfetched: GADM 4.1 ADM1 is a registered source (gadm-4.1-adm1 in scripts/sources.yaml) but the local curated GeoPackage subset (data/geodata/gadm-4.1/gadm41_adm1.gpkg) covers only 81 countries and the routing decision confirmed 0 French features are present. Per the instructions, for this route the slug itself is the correct polygon_source value and polygon_status is unassigned -- polygon_source is not set to new_source_needed or left as a route name, both of which the instructions say validate_declared_sources rejects. polygon_feature_id is left null rather than adopting the routing decision's unverified guess (FRA.1_1), because that guess was explicitly flagged in polygon_detail as needing verification once the file is fetched, and recording an unverified id as if assigned would misstate polygon_status.

## Open questions

### oq-gadm-fetch-and-gid1-verification

**Fetch full GADM 4.1 ADM1 layer for FRA and confirm Aveyron's GID_1 code**

The local curated GADM 4.1 ADM1 GeoPackage does not include France at all (0 features per the routing decision's check). To assign a polygon to this entry, the full GADM 4.1 ADM1 layer needs to be fetched or added for FRA, and Aveyron's specific GID_1 code needs to be confirmed against that file -- the routing decision's guess of FRA.1_1 is unverified and may not correspond to Aveyron once the real layer is inspected (GADM's per-country feature ordering is not alphabetical by department name in every release). Until then this entry carries polygon_status: unassigned and no feature id.

### oq-pre-1800-span-gap

**Aveyron's true origin (1790) is a decade earlier than this entry's start_year (1800)**

This entry's start_year is clamped to 1800 because the polity table has no FRA container for 1790-1800, not because Aveyron did not exist before 1800 -- it was created in March 1790 and the routing decision's span_basis documents this. If a pre-1800 FRA national container is ever added to the table (there is currently a gap between France's ancien-régime state and FRA-1800-1871), this entry's start_year, code, and container list should be revisited to extend back to 1790, and any data for Aveyron dated 1790-1800 that surfaces later should be checked against whichever container fills that gap rather than assumed to belong here.

### oq-nuts-vs-insee-boundary-vintage

**Whether the NUTS3/FRJ22 boundary used by the source data matches INSEE's current département boundary**

The routed data is keyed to NUTS3 code FRJ22, a Eurostat classification, while the territory description above uses INSEE's modern département definition. NUTS and INSEE boundaries are usually congruent for French départements, but NUTS revisions (the 2016 region merger changed NUTS2 codes, though NUTS3/département boundaries were not affected) have not been explicitly cross-checked here against INSEE's boundary history for Aveyron specifically. This matters once a GADM polygon is attached (per oq-gadm-fetch-and-gid1-verification): GADM's admin-1 boundary needs to be confirmed as congruent with both the NUTS3 unit the data is keyed to and INSEE's own département boundary before the polygon can be marked assigned rather than proxy.
