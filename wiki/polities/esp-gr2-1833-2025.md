# Granada (province of Spain)

## Summary

Granada is one of the 50 provinces created in the Javier de Burgos territorial reorganization of 30 November 1833, formed from the core of the old Kingdom of Granada in south-eastern Spain, on the Mediterranean coast of Andalusia. Its provincial capital is the city of Granada, seat of the former Nasrid emirate and the Alhambra. The province borders Málaga and Córdoba to the west, Jaén to the north, Albacete and Murcia to the east/northeast, and Almería to the east, with a short Mediterranean coastline (the Costa Tropical) to the south. This entry is `type: subnational` because sovereignty over this territory belonged to Spain throughout 1833-2025 — Granada is not an independent polity but a province within the sovereign Spanish state, and the entry exists purely to carry statistics reported at the province level, distinct from both the national ESP total and neighbouring provinces such as Almería, Málaga, or Jaén. Note the polity_code deliberately avoids the natural token `ESP-GR` because that code is already assigned in this repository to a different, non-Granada entry (a stale ESP-GR page for the old Girona/Gerona province is being deleted in this same batch as part of a de-duplication pass); `GR2` is used here to avoid colliding with whatever ESP-GR ultimately resolves to, and is flagged as a naming decision below rather than left silently ambiguous.

**Why this entry exists.** Granada is a Spanish province (unit ES614) with no existing polity match: no name match exists, and the three ESP candidates surfaced during routing (A Coruña, Madrid, and the national ESP-1800-2025 row) cover none of Granada's territory. Prior to this pipeline run, Granada-level statistical rows had no dedicated polity row — they were either left unmatched or, if folded into ESP-1800-2025, would double-count against the national Spain-wide total that already includes Granada's contribution. This entry captures province-level statistics for Granada, following the same create_new pattern already applied to the other 49 Spanish provinces created in this batch (e.g. ESP-17, ESP-A, ESP-AB, ESP-BU), all of which lacked pre-existing candidates for the identical structural reason: no prior polity row existed at the NUTS3/province granularity for Spain. Granada's status as a distinct administrative and statistical unit is confirmed by its inclusion as one of the 50 provinces instituted by the 1833 Javier de Burgos reform, a division still in force today and used by INE and IGN as the standard unit for provincial-level Spanish statistics and cartography — the same source convention already relied upon for all 49 sibling province entries in this repository.

**Territory description:** The province of Granada covers roughly 12,600 km2 in south-eastern Andalusia, spanning from the Mediterranean coast (Costa Tropical, around Motril and Almuñécar) north across the Sierra Nevada range — including Mulhacén, the highest peak on the Iberian Peninsula (3,479 m) — to the Vega de Granada basin and the semi-arid Altiplano in the province's northeast around Baza and Guadix. Its 1833 boundaries correspond closely to the modern INE/IGN province of Granada; provinces have been stable administrative units since the 1833 reform, so vintage risk for a present-day IGN boundary is low, consistent with the treatment of the other 49 provinces already using mapspain-ign.

## Decisions

### d-code-avoids-esp-gr

**Used ESP-GR2 instead of the natural ESP-GR token to avoid a code collision**

The dominant subnational naming pattern would suggest ESP-GR for Granada (from ISO 3166-2:ES-GR). However, the repository's git status for this batch shows an existing ESP-GR page (wiki/polities/esp-gr-1833-2025.md) being deleted as part of a de-duplication/repair pass in this same run, and it is not confirmed from the diff alone whether that deletion is final or whether ESP-GR will be re-created for a different province (Girona/Gerona also maps to a two-letter ISO code that could plausibly collide, though Girona's ISO 3166-2 code is actually GI, not GR). To avoid writing over or colliding with a code some other in-flight process in this same pipeline run might assign to ESP-GR, this entry uses ESP-GR2 and flags the ambiguity explicitly rather than silently picking ESP-GR. If, on inspection, ESP-GR is confirmed free and uncontested, this entry's code should be renamed to ESP-GR before merge — this is recorded as an open question below since it cannot be resolved from the routing decision alone.
